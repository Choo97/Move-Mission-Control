# 포트폴리오 케이스 스터디

이 문서는 Move Mission Control을 이력서, 포트폴리오, 면접에서 설명하기 위한 요약 자료입니다. 단순 기능 나열보다 문제 정의, 설계 판단, 구현 범위, 검증 근거를 빠르게 전달하는 데 목적이 있습니다.

## 한 줄 소개

이사 예약 접수부터 관리자 상담, 견적 안내, 고객 동의, 완료 후 리뷰까지 이어지는 운영 흐름을 Spring Boot와 React로 구현한 예약 관리 웹 서비스입니다.

## 해결하려는 문제

이사 예약은 고객 입력, 일정 확인, 견적 상담, 상태 안내, 사진 확인, 완료 후 리뷰가 서로 연결됩니다. 메신저나 전화 중심으로 처리하면 예약번호, 고객 요청, 견적 상태, 알림 이력이 분산되어 운영자가 현재 처리해야 할 일을 놓치기 쉽습니다.

이 프로젝트는 고객과 관리자의 흐름을 분리해 다음 문제를 줄이는 데 초점을 뒀습니다.

- 고객은 로그인 없이 예약을 신청하고, 예약번호와 연락처로 본인 예약만 조회합니다.
- 관리자는 접수된 예약, 고객 요청, 견적 상태, 알림 이력을 한 화면에서 확인합니다.
- 예약 수정과 취소는 고객 요청을 바로 반영하지 않고 관리자 승인 뒤 반영합니다.
- 운영시간, 휴무일, 중복 시간 예약 시도를 관리해 실제 운영 충돌을 줄입니다.

| 영역 | 구현 내용 | 면접에서 강조할 포인트 |
| --- | --- | --- |
| 고객 예약 | 예약 신청, 임시 저장, 예약번호 기반 조회 | 로그인 없는 고객 흐름에서 접근성과 개인정보 보호를 같이 고려 |
| 예약 운영 | 상태 변경, 견적 저장, 고객 견적 동의, 수정/취소 요청 승인 | 예약 도메인을 단순 CRUD가 아니라 상태 흐름으로 모델링 |
| 관리자 화면 | 예약 목록, 상세, 처리 우선순위, 알림/FAQ/리뷰 관리 | 운영자가 매일 봐야 하는 업무 단위로 화면 구성 |
| 일정 관리 | 운영시간, 휴무일, 중복 예약 시도 기록 | 예약 가능 여부를 정책으로 관리해 운영 리스크 완화 |
| 견적 정책 | 기본가, 추가요금, 거리 기준 설정과 견적 산정 스냅샷 저장 | 정책 변경 후에도 과거 예약의 견적 근거가 바뀌지 않도록 보존 |
| 알림 이력 | 이메일/SMS 발송 준비, 성공/실패 이력 관리 | 외부 연동 전에도 실패 추적 가능한 구조로 설계 |
| 리뷰 | 완료 예약 리뷰 작성, 중복 리뷰 차단, 관리자 공개/숨김/답변 | 상태 조건이 있는 고객 액션을 테스트로 방어 |
| 보안 | 관리자 인증, 예약 조회 제한, 개인정보 마스킹/암호화, 파일 업로드 검증 | 개인정보와 업로드 파일처럼 사고 가능성이 큰 부분을 우선 방어 |

## 기술 스택

- Backend: Java 17, Spring Boot 3.3.6, Spring MVC, Spring Security, Spring Data JPA
- Frontend: React, TypeScript, Vite
- View: Thymeleaf 관리자 보조 화면, React 고객/관리자 화면
- Database: MySQL for local runtime, H2 for automated tests
- Documentation: README, 실행 가이드, API 문서, 테스트 시나리오, 로드맵

## 설계 판단

### 1. 고객 요청을 즉시 반영하지 않고 승인 흐름으로 분리

예약 수정과 취소는 다른 예약 시간, 견적, 운영 준비에 영향을 줄 수 있습니다. 그래서 고객 요청은 별도 이력으로 남기고, 관리자가 승인했을 때 실제 예약 정보나 취소 상태에 반영되도록 구성했습니다.

면접 답변 예시:

> 예약 변경은 단순 update가 아니라 운영 일정과 견적에 영향을 주는 이벤트라고 봤습니다. 그래서 고객 요청과 실제 예약 상태를 분리했고, 승인/반려 이력을 남겨 운영자가 변경 근거를 추적할 수 있게 했습니다.

### 2. 관리자 화면은 처리 우선순위 중심으로 구성

관리자는 전체 예약 목록보다 지금 처리해야 할 예약, 고객 요청, 실패 알림을 먼저 봐야 합니다. README의 시연 흐름과 관리자 문서도 `고객 예약 접수 -> 관리자 처리 -> 고객 확인 -> 완료 후 리뷰` 순서로 정리했습니다.

면접 답변 예시:

> 관리자 화면은 예쁜 대시보드보다 업무 처리 속도가 중요하다고 판단했습니다. 그래서 예약 상세에서 고객 입력, 견적 상태, 고객 요청, 알림 이력을 한 흐름으로 보이게 구성했습니다.

### 3. 외부 연동은 이력 구조부터 만들고 실제 발송은 설정으로 분리

이메일과 SMS는 실제 운영 전에 비용과 발신번호, API 키 문제가 생길 수 있습니다. 프로젝트에서는 발송 이력, 상태, 실패 관리 구조를 먼저 만들고, 실제 발송은 환경변수와 provider 설정으로 켜도록 했습니다.

면접 답변 예시:

> 외부 API를 바로 강하게 결합하지 않고, 알림 이력과 실패 처리를 먼저 도메인에 넣었습니다. 덕분에 SMTP나 SMS 설정이 없어도 예약 자체는 실패하지 않고, 운영자는 나중에 실패한 알림만 재확인할 수 있습니다.

### 4. 견적 정책은 설정값과 예약 시점 스냅샷을 분리

견적 기본가와 추가요금은 운영 중 바뀔 수 있는 정책입니다. 하지만 이미 접수된 예약의 견적 산정 내역이 현재 정책 기준으로 다시 바뀌면 고객 안내와 관리자 기록이 어긋납니다. 그래서 예약 생성, 거리 입력, 예약 수정 승인 시점의 견적 산정 항목을 스냅샷으로 저장했습니다.

면접 답변 예시:

> 견적 정책은 바뀔 수 있지만 과거 예약의 견적 근거는 바뀌면 안 된다고 판단했습니다. 그래서 현재 정책 테이블과 예약별 견적 산정 스냅샷을 분리했고, 예약 상세와 PDF는 저장된 스냅샷을 우선 사용하도록 설계했습니다.

### 5. 테스트는 도메인 규칙과 보안 조건 위주로 구성

자동 테스트는 예약 상태, 견적 계산, 견적 정책 변경, 사진 업로드 확장자, 관리자 접근 권한, 리뷰 작성 조건처럼 깨지면 운영 장애로 이어지는 규칙을 중심으로 작성했습니다.

현재 검증한 자동 테스트:

```text
npm run build
npm run lint
mvn test
```

2026-07-02 기준 검증 결과:

```text
Frontend build: passed
Frontend lint: passed
Backend tests: 172 tests, 0 failures, 0 errors
```

## 이력서용 핵심 bullet

- Spring Boot와 React 기반 이사 예약 관리 서비스를 구현해 고객 예약 접수, 관리자 처리, 견적 동의, 완료 후 리뷰까지 이어지는 end-to-end 운영 흐름을 구성했습니다.
- 예약 수정/취소를 즉시 반영하지 않고 관리자 승인 기반 고객 요청 이력으로 분리해 운영 일정과 견적 변경의 추적 가능성을 확보했습니다.
- Spring Security로 관리자 영역을 보호하고, 세션 고정 방지, 동시 로그인 제한, 로그인 실패 잠금, 공개 API 접근 범위를 테스트로 검증했습니다.
- 운영시간/휴무일/중복 예약 시도/예약 운영 정책 관리를 통해 예약 가능 시간 정책을 도메인 규칙으로 분리했습니다.
- 견적 정책 설정과 예약별 견적 산정 스냅샷을 분리해 가격 정책 변경 후에도 과거 예약의 견적 근거가 유지되도록 구현했습니다.
- JUnit/Spring Boot Test 기반 자동 테스트 172개로 예약 API, 관리자 API, 보안 설정, 리뷰, 견적 계산, 파일 업로드 정책을 검증했습니다.

## 시연 순서

1. 고객 화면에서 예약을 신청하고 예약번호를 확인합니다.
2. 예약번호와 연락처로 고객 예약 상세를 조회합니다.
3. 관리자 화면에서 새 예약과 처리 우선순위를 확인합니다.
4. 관리자 상세에서 상태를 상담중/견적안내로 변경하고 견적 금액을 저장합니다.
5. 고객 상세에서 견적을 확인하고 동의합니다.
6. 관리자가 예약을 확정/완료로 변경합니다.
7. 고객이 완료 예약에 리뷰를 작성하고, 관리자가 리뷰를 관리합니다.

이 순서는 고객 경험과 관리자 운영이 연결되어 있다는 점을 가장 짧게 보여줍니다.
