# 비영리 도움 요청 랜딩페이지 정보 가이드

이 문서는 비영리 도움 요청 전용 랜딩페이지에 담아야 할 정보와 문구 기준을 정리합니다.
시각 디자인은 별도로 제작하되, 페이지가 전달해야 하는 목적, 용어, 섹션, 제외할 표현을 먼저 고정합니다.

## 목적

비영리 도움 요청 페이지는 일반 이사 예약 페이지처럼 견적과 결제를 중심으로 설명하지 않습니다.
방문자가 처음 들어왔을 때 아래 내용을 바로 이해하게 만드는 것이 목표입니다.

- 이 서비스는 이사 비용 견적 페이지가 아니라 도움 요청 접수 페이지입니다.
- 신청자는 필요한 상황과 이사 정보를 남길 수 있습니다.
- 관리자는 접수 내용을 확인한 뒤 가능 여부와 다음 안내를 전달합니다.
- 견적, 쿠폰, 결제 같은 상업적 요소는 고객 화면에서 노출하지 않습니다.

## 운영 구조

권장 URL은 `/help`입니다.

- `/`: 기본 랜딩페이지
- `/help`: 비영리 도움 요청 전용 랜딩페이지
- 관리자 운영 설정이 `NON_PROFIT`이면 `/` 접속 시 `/help`로 이동
- `/help`로 직접 접속하면 운영 설정과 관계없이 비영리 도움 요청 페이지 표시
- 일반 사용자는 운영 설정값을 직접 변경하거나 볼 수 없습니다.

이렇게 나누는 이유는 일반 예약 서비스와 비영리 도움 요청 서비스의 문맥이 다르기 때문입니다.
하나의 화면에서 조건문으로 모든 문구를 바꾸면 화면과 기능이 복잡해지므로, 첫 진입 페이지를 분리해 사용자가 이해하기 쉽게 만듭니다.

## 핵심 용어

| 일반 예약 표현 | 비영리 도움 요청 표현 |
| --- | --- |
| 이사 예약하기 | 이사 도움 요청하기 |
| 고객 | 신청자 |
| 예약 접수 | 도움 요청 접수 |
| 견적 금액 | 표시하지 않음 |
| 쿠폰/할인 | 표시하지 않음 |
| 결제 | 표시하지 않음 |
| 리뷰 | 이용 후기 또는 감사 메시지 |
| 관리자 확인 | 운영자 확인 |

`예약`이라는 단어는 완전히 금지하지 않습니다. 다만 첫 화면과 주요 버튼에서는 `도움 요청`을 우선 사용합니다.
관리자 내부에서는 기존 예약 도메인을 그대로 사용해도 됩니다. 데이터 구조를 즉시 바꾸면 변경 범위가 너무 커지기 때문입니다.

## 페이지 정보 구조

### 1. 첫 화면

첫 화면은 사용자가 바로 도움 요청을 시작할 수 있게 구성합니다.

권장 메시지:

```text
이사가 막막할 때, 도움 요청을 남겨주세요
```

보조 문구:

```text
출발지와 도착지, 이사 예정일을 남겨주시면 운영자가 내용을 확인한 뒤 가능한 도움 범위를 안내합니다.
```

주요 버튼:

```text
이사 도움 요청하기
```

보조 버튼:

```text
요청 내역 확인하기
```

### 2. 도움 대상 안내

누가 신청할 수 있는지 간단히 설명합니다.

예시 항목:

- 갑작스러운 이사 준비가 필요한 신청자
- 혼자 짐 정리가 어려운 신청자
- 이사 준비 절차를 안내받고 싶은 신청자
- 운영자가 확인 후 도움 가능 여부를 안내받고 싶은 신청자

주의할 점은 `무조건 도와드립니다`처럼 보장하는 표현을 피하는 것입니다.
운영자가 접수 내용을 확인한 뒤 가능한 범위 안에서 안내한다는 흐름을 유지합니다.

### 3. 진행 절차

비영리 도움 요청은 가격 비교보다 처리 흐름이 중요합니다.

권장 단계:

```text
STEP 01 도움 요청 정보 입력
STEP 02 요청 접수 완료
STEP 03 운영자 확인
STEP 04 가능 여부와 다음 안내 전달
STEP 05 도움 진행 또는 대체 안내
```

### 4. 요청 전 확인사항

신청자가 오해하지 않도록 책임 범위와 처리 방식을 미리 안내합니다.

필수 안내:

- 접수 후 운영자가 내용을 확인합니다.
- 접수만으로 도움 진행이 확정되는 것은 아닙니다.
- 요청 내용, 일정, 지역, 운영 상황에 따라 도움 가능 여부가 달라질 수 있습니다.
- 긴급 상황은 별도 연락 수단을 확인해야 합니다.
- 개인정보는 요청 확인과 안내 목적에만 사용합니다.

### 5. 도움 요청 입력 항목

기존 예약 입력폼을 그대로 활용하되, 화면 문구만 비영리 목적에 맞게 바꿉니다.

필수 입력:

- 신청자 이름
- 연락처
- 이사 예정일
- 희망 시간
- 출발지
- 도착지
- 이사 유형

선택 입력:

- 엘리베이터 여부
- 층수
- 사다리차 필요 여부
- 요청 메모
- 짐 사진

숨길 항목:

- 쿠폰 코드
- 할인 안내
- 결제 문구
- 견적 금액

### 6. 요청 내역 확인

신청자는 접수 후 요청번호와 연락처로 진행 상태를 확인할 수 있어야 합니다.

권장 문구:

```text
요청번호와 연락처를 입력하면 접수 상태와 운영자 안내를 확인할 수 있습니다.
```

상태 표현은 기존 예약 상태를 재사용하되, 고객 화면에서는 부드럽게 바꿔 보여줍니다.

| 내부 상태 | 신청자 화면 문구 |
| --- | --- |
| 접수 | 요청 접수 |
| 상담중 | 내용 확인 중 |
| 확정 | 도움 진행 예정 |
| 완료 | 도움 완료 |
| 취소 | 요청 취소 |

### 7. 이용 후기 또는 감사 메시지

리뷰는 상업 서비스 평가처럼 보이지 않게 표현합니다.

권장 제목:

```text
이용 후기
```

또는:

```text
감사 메시지
```

권장 설명:

```text
도움을 요청한 신청자들이 남긴 이야기를 소개합니다.
```

피해야 할 표현:

- 평점으로 서비스 품질을 과하게 광고하는 문구
- `만족도 100%`처럼 증명하기 어려운 문구
- `관리자가 공개 처리한 리뷰`처럼 내부 작업용 표현

### 8. 하단 정보

푸터에는 최소한의 운영 정보를 둡니다.

필수 정보:

- 서비스명
- 운영 주체
- 연락처 또는 문의 이메일
- 개인정보처리방침
- 이용 안내 또는 약관

사업자 정보가 없는 개인/비영리 목적 운영 단계라면 `사업자등록번호`처럼 없는 정보를 억지로 넣지 않습니다.
다만 실제 서비스를 운영한다면 운영 주체와 책임 범위는 반드시 명확히 적어야 합니다.

## 피해야 할 표현

아래 표현은 법적 오해나 사용자 오해를 만들 수 있으므로 사용하지 않습니다.

- `공식 비영리단체`
- `비영리법인`
- `공익기관`
- `무료 이사 보장`
- `무조건 지원`
- `즉시 배정`
- `견적 최저가`
- `할인`
- `결제`
- `수익 없음 보장`

비영리 법인이나 공식 단체가 아닌 단계에서는 `비영리 목적의 도움 요청 서비스`처럼 조심스럽게 표현합니다.

## 관리자 설정과 연결 기준

관리자 운영 설정은 고객에게 직접 보여주는 기능이 아니라, 고객 화면 방향을 결정하는 내부 설정입니다.

권장 동작:

- `GENERAL`: `/`에서 일반 랜딩페이지 표시
- `NON_PROFIT`: `/` 접속 시 `/help`로 이동
- `/help`: 비영리 도움 요청 페이지 직접 표시
- `/reservations/new`: 운영 모드가 `NON_PROFIT`이면 입력폼 문구를 도움 요청 중심으로 표시
- `/reservations/{id}`: 운영 모드가 `NON_PROFIT`이면 견적 금액, 쿠폰, 결제 느낌의 정보를 숨김

리다이렉트는 무한 반복이 생기지 않게 `/help`에서는 다시 `/help`로 이동하지 않아야 합니다.

## 구현 시 확인할 항목

- 비영리 모드에서 `/` 접속 시 `/help`로 이동하는가
- `/help` 직접 접속이 가능한가
- 일반 모드에서는 `/`가 기존 랜딩페이지를 유지하는가
- 비영리 페이지에서 견적, 쿠폰, 결제 문구가 보이지 않는가
- 도움 요청 버튼이 기존 예약 작성 화면으로 자연스럽게 이어지는가
- 요청 내역 확인 버튼이 기존 예약 조회 화면으로 이어지는가
- 관리자 설정 화면은 일반 사용자에게 노출되지 않는가
- 개인정보처리방침과 이용 안내 링크가 제공되는가

## 포트폴리오 설명 포인트

이 기능은 단순히 문구를 바꾸는 작업이 아니라, 운영 목적에 따라 고객 진입 경험을 분리하는 설계입니다.

면접이나 포트폴리오에서는 아래처럼 설명할 수 있습니다.

```text
일반 예약 서비스와 비영리 도움 요청 서비스는 사용자가 기대하는 정보가 달라서,
운영 설정값에 따라 고객 첫 진입 페이지를 분리했습니다.
백엔드 도메인은 기존 예약 구조를 유지해 변경 범위를 줄이고,
고객 화면에서는 견적/쿠폰/결제 요소를 숨겨 비영리 목적에 맞는 흐름을 제공했습니다.
```
