# 전체 테스트 시나리오

이 문서는 Move Mission Control을 직접 실행한 뒤, 고객과 관리자의 주요 흐름을 어떤 순서로 확인하면 되는지 정리합니다.

자동 테스트는 코드가 깨졌는지 빠르게 확인하는 용도이고, 이 문서는 실제 화면에서 서비스가 자연스럽게 동작하는지 확인하는 수동 테스트 기준입니다.

## 테스트 전 준비

백엔드와 프론트엔드를 각각 실행합니다.

```bash
bash run-backend.sh
bash run-frontend.sh
```

접속 주소는 아래와 같습니다.

```text
고객 React 화면  http://localhost:5173/
React 관리자 화면 http://localhost:5173/admin/reservations
백엔드 화면      http://localhost:8081/
기존 관리자 화면 http://localhost:8081/admin/reservations
```

관리자 기본 계정은 로컬 개발용입니다.

```text
ID       admin
Password admin1234
```

## 1. 고객 예약 신청 흐름

고객이 실제로 예약을 접수할 수 있는지 확인합니다.

1. `http://localhost:5173/`에 접속합니다.
2. `이사 예약하기` 버튼을 누릅니다.
3. 고객명, 연락처, 이메일, 출발지, 도착지, 이사 희망일, 주거 조건을 입력합니다.
4. 짐 규모와 요청사항을 입력합니다.
5. 예약을 제출합니다.
6. 예약 완료 화면에서 예약번호가 표시되는지 확인합니다.

확인 기준:

- 필수값이 없으면 안내 문구가 표시됩니다.
- 예약이 성공하면 예약번호와 조회 안내가 표시됩니다.
- 예약 완료 후 고객이 예약 조회로 이동할 수 있습니다.

## 2. 고객 예약 조회 흐름

고객이 예약번호와 연락처로 본인 예약만 조회할 수 있는지 확인합니다.

1. `http://localhost:5173/`에 접속합니다.
2. `예약 조회하기` 버튼을 누릅니다.
3. 방금 생성한 예약번호와 연락처를 입력합니다.
4. 예약 상세 화면으로 이동하는지 확인합니다.
5. 잘못된 연락처로 다시 조회해 실패 안내가 나오는지 확인합니다.

확인 기준:

- 올바른 예약번호와 연락처를 입력하면 예약 상세가 보입니다.
- 연락처가 다르면 예약 정보가 노출되지 않습니다.
- 고객에게는 내부 관리자용 정보가 보이지 않습니다.

## 3. 고객 예약 수정 및 취소 흐름

예약 접수 후 고객이 필요한 변경을 요청할 수 있는지 확인합니다.

1. 고객 예약 상세 화면에 접속합니다.
2. 예약 수정 화면으로 이동합니다.
3. 요청사항이나 주소 같은 정보를 변경합니다.
4. 수정 요청 접수 안내와 처리 대기 표시가 보이는지 확인합니다.
5. 관리자 예약 상세 화면에서 고객 요청을 승인합니다.
6. 고객 예약 상세 화면에서 변경 내용이 반영되는지 확인합니다.
7. 취소 요청을 진행하고 처리 대기 표시가 보이는지 확인합니다.
8. 관리자 예약 상세 화면에서 취소 요청을 승인합니다.
9. 고객 예약 상세 화면에서 상태가 취소로 바뀌는지 확인합니다.

확인 기준:

- 수정 가능한 상태에서만 수정이 가능합니다.
- 수정 또는 취소 요청은 승인 전까지 실제 예약에 반영되지 않습니다.
- 고객 요청 이력에는 처리 대기, 승인, 반려 상태가 남습니다.
- 취소된 예약은 이후 견적 동의 같은 진행 작업이 제한됩니다.

## 4. 관리자 예약 확인 흐름

관리자가 새 예약을 확인하고 운영 처리를 시작할 수 있는지 확인합니다.

1. `http://localhost:5173/admin/reservations`에 접속합니다.
2. 관리자 계정으로 로그인합니다.
3. 예약 목록 상단의 처리 우선순위 요약을 확인합니다.
4. 방금 생성한 예약이 목록에 보이는지 확인합니다.
5. 예약 상세 화면으로 이동합니다.
6. 고객 흐름 요약에서 다음 처리, 고객 입력, 견적 상태, 알림 상태를 확인합니다.

확인 기준:

- 접수 대기 예약 수와 고객 요청 대기 수가 실제 예약 상태와 맞습니다.
- 목록에서는 전체 운영 우선순위가 보입니다.
- 상세에서는 예약 1건의 다음 처리 기준이 보입니다.

관리자 상세 화면 UI 확인 기준:

- 고객 흐름 요약, 현장 정보와 짐 사진, 운영 처리, 고객 요청 처리, 운영 이력, 알림 이력 순서로 표시됩니다.
- 긴 주소, 긴 파일명, 긴 현재 할 일 문구가 패널 밖으로 삐져나가지 않습니다.
- 상태 변경 버튼, 이동 거리 입력창, 거리 저장 버튼, 견적 저장 버튼이 서로 겹치지 않습니다.
- 알림 발송 버튼은 좁은 화면에서도 다음 줄로 내려가며 읽을 수 있습니다.

이 UI 확인을 따로 두는 이유는 React 관리자 상세 화면이 오른쪽 패널 안에서 동작하기 때문입니다. 브라우저 전체 폭은 넓어도 실제 상세 패널은 좁을 수 있으므로, 고정 2칸 또는 3칸 배치가 글자 겹침을 만들지 않는지 확인해야 합니다.

## 5. 관리자 견적 및 상태 변경 흐름

관리자가 예약을 상담하고 견적을 안내할 수 있는지 확인합니다.

1. 예약 상세 화면에서 상태를 `상담중`으로 변경합니다.
2. 관리자 메모를 입력합니다.
3. 이동 거리나 견적 금액을 저장합니다.
4. 상태를 `견적안내`로 변경합니다.
5. 고객 예약 상세 화면에서 견적 안내 상태가 보이는지 확인합니다.

확인 기준:

- 상태 변경 후 목록과 상세 화면에 같은 상태가 표시됩니다.
- 견적 금액이 고객 상세 화면에 표시됩니다.
- 상태 변경 이력이 관리자 화면에 남습니다.

## 6. 고객 견적 동의 및 예약 확정 흐름

고객이 안내받은 견적에 동의하고 예약이 확정되는지 확인합니다.

1. 고객 예약 상세 화면에 접속합니다.
2. 견적 금액과 안내 문구를 확인합니다.
3. 견적 동의 버튼을 누릅니다.
4. 관리자 예약 상세 화면에서 고객 동의 상태를 확인합니다.
5. 관리자가 상태를 `확정`으로 변경합니다.

확인 기준:

- 고객 동의 전후 상태가 구분됩니다.
- 관리자는 고객 동의 여부를 확인한 뒤 확정 처리할 수 있습니다.
- 확정 상태는 고객 진행 단계에도 반영됩니다.

## 7. 짐 사진 업로드 흐름

고객이 짐 상태를 사진으로 전달할 수 있는지 확인합니다.

1. 고객 예약 상세 화면에 접속합니다.
2. 사진 업로드 영역에서 이미지 파일을 선택합니다.
3. 업로드 후 사진 목록이 표시되는지 확인합니다.
4. 관리자 예약 상세 화면에서 사진 업로드 여부를 확인합니다.

확인 기준:

- 이미지 파일은 업로드됩니다.
- 허용하지 않는 파일 형식은 거부됩니다.
- 관리자는 고객 입력 요약에서 사진 제출 여부를 빠르게 알 수 있습니다.

## 8. 완료 후 리뷰 작성 흐름

이사가 완료된 뒤 고객 리뷰를 남길 수 있는지 확인합니다.

1. 관리자가 예약 상태를 `완료`로 변경합니다.
2. 고객 예약 상세 화면에 접속합니다.
3. 별점과 리뷰 내용을 입력합니다.
4. 리뷰를 제출합니다.
5. `http://localhost:5173/admin/reviews`에 접속합니다.
6. 관리자 계정으로 로그인합니다.
7. 관리자 리뷰 관리 화면에서 리뷰가 보이는지 확인합니다.
8. 평점 필터, 공개 상태 필터, 검색어가 적용되는지 확인합니다.
9. `숨김 처리`를 눌렀을 때 리뷰 상태가 숨김으로 바뀌는지 확인합니다.
10. `공개 처리`를 눌렀을 때 리뷰 상태가 다시 공개로 바뀌는지 확인합니다.
11. `예약 상세`를 눌러 해당 예약 상세로 이동할 수 있는지 확인합니다.

확인 기준:

- 완료된 예약만 리뷰 작성이 가능합니다.
- 같은 예약에 중복 리뷰를 작성할 수 없습니다.
- 관리자 화면에서 리뷰와 평점, 평균 평점, 3점 이하 확인 필요 건수를 확인할 수 있습니다.
- 관리자는 리뷰 원문을 삭제하지 않고 공개/숨김 상태만 변경할 수 있습니다.
- 리뷰에서 연결된 예약 상세로 이동할 수 있습니다.

## 9. 일정 및 휴무일 확인 흐름

예약 가능 시간이 운영 정책과 충돌하지 않는지 확인합니다.

1. 관리자 화면에서 요일별 운영시간과 지정 휴무일을 설정합니다.
2. 고객 예약 화면에서 휴무일을 선택해 봅니다.
3. 이미 예약된 시간대와 같은 시간으로 예약을 시도합니다.
4. 고객에게 예약 불가 안내가 표시되는지 확인합니다.
5. 관리자 화면에서 중복 예약 시도 이력이 남는지 확인합니다.

확인 기준:

- 휴무일과 운영시간 외 시간은 예약할 수 없습니다.
- 중복 시간 예약은 고객에게 안내됩니다.
- 관리자는 해당 시간에 예약하려던 고객이 있었다는 사실을 확인할 수 있습니다.

## 10. 이메일/SMS 알림 이력 확인 흐름

SMTP와 SMS 설정 여부와 관계없이 알림 이력이 관리되는지 확인합니다.

1. 이메일을 입력한 예약을 생성합니다.
2. React 관리자 예약 목록 상단의 `알림 처리 대상` 영역을 확인합니다.
3. SMTP 설정이 꺼져 있다면 이메일 실패 이력으로 기록되는지 확인합니다.
4. SMS 설정이 꺼져 있다면 SMS 실패 이력으로 기록되는지 확인합니다.
5. 실패 알림이 발송 대기 알림보다 먼저 보이는지 확인합니다.
6. `http://localhost:5173/admin/notifications`에서 전체 알림 이력을 확인합니다.
7. 채널, 상태, 검색어 필터가 적용되는지 확인합니다.
8. `예약 상세`를 눌러 해당 예약의 알림 이력으로 이동할 수 있는지 확인합니다.
9. 실패 이력이 처리 우선순위 요약에 반영되는지 확인합니다.

확인 기준:

- 이메일 발송 시도 이력이 남습니다.
- SMS 발송 시도 이력이 남습니다.
- 실패한 이메일과 SMS는 관리자에게 확인 대상으로 표시됩니다.
- 실패 알림은 목록의 `알림 처리 대상`에서 발송 대기보다 먼저 표시됩니다.
- 전체 알림 이력 화면에서는 채널, 상태, 검색어로 필요한 이력을 좁혀 볼 수 있습니다.
- SMTP 또는 SMS 설정이 없어도 예약 자체는 정상 접수됩니다.

## 11. 관리자 FAQ 관리 흐름

고객에게 보이는 자주 묻는 질문을 관리자가 React 화면에서 관리할 수 있는지 확인합니다.

1. `http://localhost:5173/admin/faqs`에 접속합니다.
2. 관리자 계정으로 로그인합니다.
3. 새 FAQ 질문, 답변, 정렬 순서를 입력해 추가합니다.
4. 추가된 FAQ가 목록에 표시되는지 확인합니다.
5. 질문, 답변, 정렬 순서를 수정해 저장합니다.
6. FAQ를 숨김 처리한 뒤 고객 FAQ 화면에서 보이지 않는지 확인합니다.
7. 다시 공개 처리한 뒤 고객 FAQ 화면에 표시되는지 확인합니다.

확인 기준:

- 관리자 FAQ 화면에는 전체, 공개, 숨김 건수가 표시됩니다.
- 공개 FAQ만 고객 FAQ 화면에 표시됩니다.
- 숨김 FAQ는 관리자 화면에는 남아 있지만 고객 화면에는 표시되지 않습니다.
- 잘못된 입력은 오류 안내를 보여주고 저장하지 않습니다.

## 12. 자동 테스트 실행

수동 확인 전후로 자동 테스트를 실행해 기본 기능이 깨지지 않았는지 확인합니다.

```bash
mvn clean test
```

확인 기준:

- 모든 테스트가 통과합니다.
- 실패가 있다면 기능을 추가하기 전에 먼저 원인을 확인합니다.

## 추천 확인 순서

혼자 개발할 때는 매번 모든 항목을 확인하기 어렵습니다. 그래서 작업 종류에 따라 아래처럼 나눠 확인합니다.

| 작업 종류 | 우선 확인할 시나리오 |
| --- | --- |
| 고객 화면 수정 | 1, 2, 3, 6 |
| 관리자 화면 수정 | 4, 5, 9, 10, 11 |
| 예약 상태 로직 수정 | 1, 2, 4, 5, 6 |
| 사진/리뷰 기능 수정 | 7, 8 |
| 관리자 리뷰 화면 수정 | 8 |
| FAQ 기능 수정 | 11 |
| 운영시간/휴무일 수정 | 9 |
| 배포 전 최종 확인 | 1부터 12까지 전체 확인 |

이렇게 나누는 이유는 모든 테스트를 매번 다 하면 개발 속도가 느려지기 때문입니다. 대신 수정한 기능과 직접 연결된 흐름은 반드시 확인하고, 배포 전에는 전체 흐름을 한 번에 점검합니다.
