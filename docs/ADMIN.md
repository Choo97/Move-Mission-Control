# 관리자 화면 및 운영 구조

이 문서는 관리자 메뉴, 대시보드, 예약 운영 화면의 설계 의도를 정리합니다.

## 화면 테마

초기 화면은 밝은 흰색 배경에 코랄 오렌지 포인트를 섞은 따뜻한 예약 플랫폼 방향으로 구성했습니다.

- 기본 배경: 흰색, 연한 코랄
- 포인트 컬러: 코랄 오렌지, 짙은 브라운
- UI: 카드형 예약/관리 화면
- 분위기: 따뜻한 예약 플랫폼 + 관제 보드

색상 테마는 화면 오른쪽 아래 전환 버튼으로 비교할 수 있습니다.

- `코랄`: 현재 기본 테마입니다. 붉은색과 주황색 사이의 따뜻한 느낌을 주되, 빨간색 경고 화면처럼 보이지 않도록 코랄 오렌지 계열로 조정했습니다.
- `하늘`: 이전 기본 테마입니다. 신뢰감과 깔끔한 예약 플랫폼 느낌을 비교할 수 있도록 보존했습니다.

선택한 테마는 브라우저 `localStorage`에 저장되어 다른 화면으로 이동해도 유지됩니다.

## 관리자 메뉴 구조

관리자 기능이 늘어나면서 상단 메뉴를 모두 나열하면 화면이 복잡해지고, 운영자가 자주 쓰는 기능을 찾기 어려워집니다. 그래서 관리자 메뉴는 아래 기준으로 묶었습니다.

- `예약 관리`: 예약 목록, 견적 기준, 알림 이력처럼 매일 확인하는 예약 처리 기능
- `운영 관리`: 리뷰, FAQ, 쿠폰처럼 고객 경험과 운영 정책을 관리하는 기능
- `시스템 관리`: 감사 로그, 계정, 비밀번호처럼 보안과 운영 이력을 관리하는 기능

## 관리자 접근 권한 기준

현재 MVP 단계에서는 관리자 역할을 세분화하지 않고 `ADMIN` 권한 하나로 운영합니다. 혼자 운영하는 단계에서 예약 담당, 정산 담당, 시스템 담당처럼 권한을 미리 나누면 관리할 규칙이 많아지고 실제 개발 속도가 느려질 수 있기 때문입니다.

접근 기준은 아래처럼 단순하게 고정했습니다.

- 고객 화면과 고객 API는 로그인 없이 접근 가능
- `/admin/**` 관리자 화면은 로그인한 `ADMIN` 권한만 접근 가능
- `/api/admin/**` 관리자 API는 로그인한 `ADMIN` 권한만 접근 가능
- 로그인하지 않은 사용자가 관리자 화면에 접근하면 로그인 화면으로 이동
- 로그인하지 않은 사용자가 관리자 API에 접근하면 `401 Unauthorized` 응답
- 로그인했지만 `ADMIN` 권한이 없으면 `403 Forbidden` 응답

이 기준을 테스트로 고정해 둔 이유는 이후 React 관리자 화면이나 권한 분리 작업을 하더라도, 고객 공개 영역과 관리자 보호 영역이 섞이지 않게 하기 위해서입니다.

## 서비스 운영 방식 설정

운영 설정에는 `일반 이사 예약`과 `비영리 도움 요청` 모드를 둡니다.

- 일반 사용자는 운영 방식을 선택하거나 변경할 수 없습니다.
- 운영 방식 변경은 로그인한 관리자만 `/admin/availability` 운영 설정 화면에서 할 수 있습니다.
- 운영 설정 화면에는 일반 모드와 비영리 모드의 고객 화면 적용 차이를 비교 표로 보여줍니다.
- 고객 공개 API는 전체 운영 정책을 노출하지 않고 현재 운영 방식 값만 제공합니다.
- 비영리 도움 요청 모드에서는 고객 화면의 문구를 `예약`보다 `도움 요청` 중심으로 바꾸고, 견적 금액과 쿠폰 같은 상업적 요소를 숨깁니다.

이렇게 나눈 이유는 일반 사용자가 내부 운영 설정을 볼 필요가 없기 때문입니다. 고객에게는 현재 서비스가 어떤 방식으로 운영되는지만 화면 문구와 노출 기능으로 자연스럽게 전달하고, 실제 정책 변경 권한은 관리자에게만 둡니다.

## React 관리자 전환 기준

관리자 화면은 기존 Thymeleaf 화면을 바로 제거하지 않고, React 화면을 별도 경로에서 먼저 검증합니다.

- React 관리자 1차 화면: `http://localhost:5173/admin/reservations`
- 기존 관리자 화면: `http://localhost:8081/admin/reservations`
- 1차 전환 범위: 예약 목록, 예약 상세, 상태 변경, 거리 저장, 견적 저장, 관리자 메모, 고객 수정/취소 요청 승인/반려, 예약별 알림 발송, 알림 이력 목록, FAQ 관리, 리뷰 관리
- 기존 유지 범위: 달력, 운영 설정, 쿠폰, 감사 로그, 계정 관리

이렇게 나누는 이유는 관리자 기능이 예약 운영에 직접 영향을 주기 때문입니다. React 화면에서 핵심 흐름을 먼저 검증하고, 문제가 있으면 기존 Thymeleaf 화면으로 즉시 돌아갈 수 있게 유지합니다.

## 고객 흐름 요약

관리자 예약 상세 화면 상단에는 고객 흐름 요약을 배치합니다.

- 다음 처리: 현재 상태에서 관리자가 먼저 해야 할 일을 한 문장으로 표시
- 고객 입력: 고객 요청사항과 짐 사진 업로드 여부 표시
- 고객 요청: 고객이 보낸 수정 또는 취소 요청의 처리 대기 여부 표시
- 견적 상태: 최종 견적과 고객 동의 여부 표시
- 알림 상태: 이메일 발송 준비 또는 실패 여부 표시
- 흐름 단계: 예약 접수, 정보 확인, 거리/견적 점검, 견적 안내, 고객 동의 단계 표시

이 요약을 먼저 보여주는 이유는 관리자가 예약 상세 전체를 읽기 전에 현재 운영상 필요한 조치를 빠르게 판단할 수 있게 하기 위해서입니다.

## React 관리자 예약 상세 구성

React 관리자 예약 상세 화면은 오른쪽 상세 패널 안에서 예약 1건을 처리하는 구조입니다.

- `고객 흐름 요약`: 현재 예약에서 가장 먼저 볼 판단 정보를 상단에 둡니다.
- `기본 예약 정보`: 연락처, 이메일, 이사일, 주소, 거리, 최종 견적을 확인합니다.
- `현장 정보와 짐 사진`: 출발지/도착지 조건과 짐 사진을 운영 처리 전에 확인합니다.
- `운영 처리`: 상태 변경, 이동 거리 저장, 견적 저장, 관리자 메모를 한곳에서 처리합니다.
- `고객 요청 처리`: 고객 수정/취소 요청이 있으면 승인 또는 반려합니다.
- `운영 이력`: 상태 변경, 고객 행동, 감사 로그를 시간 흐름대로 확인합니다.
- `알림 이력`: 이메일/SMS 발송 대기, 완료, 실패 상태를 확인하고 필요한 알림을 발송합니다.

이 순서로 배치한 이유는 관리자가 고객 상황을 먼저 이해한 뒤 운영 작업을 수행하고, 마지막에 이력과 알림을 확인하는 흐름이 자연스럽기 때문입니다.

상세 패널은 화면 전체보다 실제 표시 폭이 좁습니다. 그래서 내부 카드는 고정 2칸이나 3칸 배치를 피하고, 패널 폭에 맞춰 자동으로 1칸 또는 여러 칸으로 바뀌게 구성합니다. 상태 배지, 현재 할 일, 알림 버튼처럼 길어질 수 있는 요소는 한 줄에 억지로 넣지 않고 다음 줄로 내려갈 수 있게 합니다.

이렇게 한 이유는 관리자 상세 화면에서 주소, 파일명, 안내 문구, 버튼이 겹치면 운영자가 예약 정보를 잘못 읽을 수 있기 때문입니다. 기능이 정상이어도 화면이 깨지면 실제 운영에서는 처리 실수가 생길 수 있습니다.

## 처리 우선순위 요약

관리자 예약 목록 상단에는 전체 운영 기준의 처리 우선순위 요약을 배치합니다.

- 접수 대기: 아직 상담 시작이 필요한 예약 수
- 상담 진행: 상담 메모와 견적 확인이 필요한 예약 수
- 고객 요청 대기: 고객이 보낸 수정 또는 취소 요청 중 아직 승인/반려하지 않은 건수
- 고객 동의 대기: 견적 안내 후 고객 동의가 필요한 예약 수
- 거리 확인 필요: 거리 입력 후 견적 점검이 필요한 예약 수
- 이메일 실패: 이메일 발송 실패 이력 확인이 필요한 건수

목록 요약은 전체 운영 상황을 보는 용도이고, 상세 요약은 선택한 예약 1건의 다음 처리를 보는 용도입니다. 두 영역을 분리해 관리자가 목록에서는 우선순위를 판단하고, 상세에서는 개별 예약 처리를 이어갈 수 있게 합니다.

로그인 전 화면에서는 내부 관리자 메뉴를 노출하지 않고 `관리자 로그인`만 보여줍니다. 로그인 전 사용자는 아직 운영 권한이 없기 때문에, 접근 가능한 행동만 보여주는 편이 화면도 단순하고 보안 흐름도 명확합니다.

## 알림 처리 대상 모아보기

React 관리자 예약 목록에는 `알림 처리 대상` 영역을 배치합니다.

- 실패 알림: 고객에게 안내가 전달되지 않았을 가능성이 있어 가장 먼저 표시합니다.
- 발송 대기 알림: 아직 고객에게 보내지 않은 안내이므로 실패 알림 다음으로 표시합니다.
- 예약 상세 이동: 각 알림에서 바로 해당 예약 상세를 열어 알림 이력과 운영 상태를 함께 확인합니다.

이 영역을 예약 목록 상단에 둔 이유는 관리자가 예약 상세를 하나씩 열기 전에 고객 안내 누락 가능성이 있는 건을 먼저 발견해야 하기 때문입니다. 알림은 예약 처리 결과와 연결되어 있으므로 전체 알림 관리 화면보다 예약 목록의 운영 우선순위 근처에서 확인하는 편이 실제 업무 흐름에 더 맞습니다.

## 전체 알림 이력 화면

React 관리자 화면에는 `/admin/notifications` 알림 이력 목록을 제공합니다.

- 채널 필터: 이메일, SMS, 카카오 알림톡 기준으로 좁혀 봅니다.
- 상태 필터: 발송 준비, 발송 완료, 발송 실패 기준으로 좁혀 봅니다.
- 검색어: 고객명, 연락처, 이메일, 알림 수신처로 찾습니다.
- 요약 지표: 현재 조건의 전체, 실패, 발송 대기, 발송 완료 건수를 표시합니다.
- 예약 상세 이동: 알림을 확인한 뒤 해당 예약 상세로 바로 이동합니다.

알림 처리 대상은 급한 건을 먼저 보는 화면이고, 전체 알림 이력은 “언제 어떤 안내를 누구에게 보내려 했는지”를 추적하는 화면입니다. 두 화면을 나눈 이유는 운영자가 당장 처리할 일과 과거 기록 확인을 같은 목록에서 섞어 보면 우선순위가 흐려지기 때문입니다.

## FAQ 관리 화면

React 관리자 화면에는 `/admin/faqs` FAQ 관리 화면을 제공합니다.

- FAQ 추가: 고객이 자주 묻는 질문과 답변을 등록합니다.
- FAQ 수정: 질문, 답변, 정렬 순서를 수정합니다.
- 공개/숨김: 고객 화면 노출 여부를 관리합니다.
- 고객 FAQ 보기: 실제 고객이 보는 `/?view=faq` 흐름으로 이동해 확인합니다.
- 요약 지표: 전체, 공개, 숨김 FAQ 수를 표시합니다.

FAQ 관리를 React로 전환한 이유는 고객 이용 안내 화면과 직접 연결되기 때문입니다. 고객에게 보이는 문구를 관리자가 직접 바꾸고 바로 고객 화면에서 확인할 수 있으면, 작은 안내 변경 때문에 Java 코드를 수정하거나 서버 템플릿을 만질 필요가 줄어듭니다.

## 리뷰 관리 화면

React 관리자 화면에는 `/admin/reviews` 리뷰 관리 화면을 제공합니다.

- 리뷰 요약: 전체 리뷰 수, 현재 필터 결과, 평균 평점, 3점 이하 확인 필요 건수를 표시합니다.
- 평점 필터: 1점부터 5점까지 원하는 평점만 좁혀 봅니다.
- 공개 상태 필터: 공개 리뷰와 숨김 리뷰를 구분해 확인합니다.
- 검색: 고객명, 연락처, 리뷰 내용, 예약번호로 리뷰를 찾습니다.
- 리뷰 카드: 공개 상태, 평점, 리뷰 내용, 고객 정보, 이사 일정, 작성일을 함께 표시합니다.
- 공개/숨김 처리: 고객이 작성한 원본 내용은 유지하고, 노출 가능 여부만 변경합니다.
- 관리자 답변: 리뷰별로 대응 답변을 저장하고, 답변 작성자와 작성 시각을 함께 남깁니다.
- 예약 상세 이동: 리뷰가 연결된 예약 상세로 바로 이동합니다.

리뷰 관리를 React로 전환한 이유는 고객 피드백이 예약 운영 품질을 보여주는 자료이기 때문입니다. 관리자 화면에서 낮은 평점과 고객 의견을 빠르게 확인하고 해당 예약 상세로 이동할 수 있으면, 단순 리뷰 목록보다 실제 운영 개선 흐름을 설명하기 좋습니다. 고객이 작성한 원본 피드백은 임의 수정하지 않고 공개/숨김 상태와 관리자 답변만 관리하도록 구성했습니다. 이렇게 하면 부적절하거나 아직 확인이 필요한 리뷰를 숨기면서도 원본 데이터와 대응 기록은 보존할 수 있습니다.

## 관리자 대시보드 구조

관리자 첫 화면은 전체 예약 수만 보여주는 화면이 아니라, 운영자가 오늘 무엇을 먼저 처리해야 하는지 판단하는 화면으로 구성했습니다.

### 대시보드 핵심 영역

- `요약 지표`: 전체 예약, 접수, 상담중, 견적안내, 확정, 완료 등 현재 운영 상태를 숫자로 확인합니다.
- `오늘 해야 할 일`: 접수 대기, 상담중, 고객 요청 대기, 고객 동의 대기, 거리 확인 필요, 이메일 실패처럼 즉시 처리할 항목을 모아 보여줍니다.
- `최근 예약/리뷰`: 새로 들어온 예약과 고객 피드백을 빠르게 확인합니다.

### 예약 운영 흐름

- 예약 목록은 기본적으로 처리 우선순위 기준으로 정렬합니다.
- 검색, 상태 필터, 이사일 기간 필터, 빠른 기간 필터로 필요한 예약만 좁혀 볼 수 있습니다.
- 예약이 많아질 때를 대비해 목록 페이징과 표시 건수 선택을 제공합니다.
- 현재 필터와 정렬 조건을 유지한 채 CSV로 다운로드할 수 있습니다.

### 일정 관리

- `이사 일정 달력`에서 월간 예약 분포와 선택 날짜의 일정을 함께 확인합니다.
- 예약 상태별 색상, 오늘 일정 강조, 선택 날짜 일정 카드로 일정 확인 속도를 높였습니다.
- 달력에서도 상세 이동, 날짜별 목록 확인, CSV 다운로드, 상태 빠른 변경을 할 수 있습니다.

### 상세 처리

- 예약 상세 화면 상단에는 현재 예약에서 먼저 처리해야 할 일을 표시합니다.
- 오른쪽 처리 영역에는 고객 요청 승인/반려, 상태 변경, 견적 저장, 거리 저장, 메모 저장, 이메일 발송처럼 자주 쓰는 작업을 모았습니다.
- 상태 변경처럼 운영 이력에 영향을 주는 작업은 확인 메시지와 감사 로그를 남깁니다.
- 상세 화면에서 목록으로 돌아갈 때 기존 필터, 정렬, 페이지 위치를 유지합니다.

## 고객 예약 상세 화면 기준

고객 예약 상세 화면에는 예약 진행 상태를 `접수 -> 상담중 -> 견적안내 -> 확정 -> 완료` 단계로 보여줍니다. 고객은 관리자처럼 내부 상태를 알 필요가 없기 때문에, 현재 단계와 다음에 할 일 중심으로 안내해 예약 진행 상황을 쉽게 이해할 수 있도록 했습니다.

고객 예약 상세 화면에는 현재 상태별 고객 안내도 함께 표시합니다. 상태만 보여주면 고객이 실제로 무엇을 준비해야 하는지 모를 수 있으므로, 연락 준비, 현장 조건 확인, 견적 동의, 이사 전 준비처럼 고객 행동으로 이어지는 내용을 예약 진행 상태 바로 아래에 배치했습니다.

고객 안내 문구는 관리자 `운영 관리 > 고객 안내` 화면에서 관리합니다. 안내 문구는 예약 상태별로 등록하고 정렬 순서를 지정할 수 있으며, 공개 또는 숨김 처리할 수 있습니다. 이렇게 분리하면 고객에게 보여줄 문구를 바꿀 때 Java 코드를 수정하지 않아도 됩니다.

고객이 예약을 수정하거나 취소하면 바로 예약을 바꾸지 않고 고객 요청으로 저장합니다. 관리자는 예약 상세 화면에서 요청 내용을 확인한 뒤 승인하거나 반려합니다. 수정 요청을 승인하면 실제 예약 정보가 바뀌고, 취소 요청을 승인하면 예약 상태가 `취소`로 변경됩니다.

이 방식을 선택한 이유는 이사 예약의 일정, 주소, 취소가 배차와 견적에 직접 영향을 주기 때문입니다. 고객에게는 셀프 요청 기능을 제공하면서도, 운영자는 변경 내용을 확인한 뒤 반영할 수 있습니다. 고객 요청 이력은 고객 상세 화면과 관리자 예약 상세 화면에서 함께 확인할 수 있어 운영자가 예약 변경 과정을 놓치지 않도록 했습니다.
